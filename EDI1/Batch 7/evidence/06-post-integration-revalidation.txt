Root cause, stated precisely
----------------------------
Batch 7 claim 2 declares three service lines over seed block 2, which has
two loops, so line 3 is fabricated. The two merged implementations disagree:

  main            generate.py: copies the block's ORIGINAL loops round-robin
                  (its comments cite an internal "Ruling T5-f"), so line 3 is
                  a copy of seed line 1:
                    SV2*0430*HC:97530*100.00*UN*3
                    HCP*10*85.00*15.00*9327*0.00**0.00****UN*3

  837p-seed-      generate.py splice_to(): "Added loops are copies of the
  registration    block's last loop", so it expects a copy of seed line 2:
  (authoritative)   SV2*0440*HC:92507*...*UN*1
                    HCP*10*326.40*57.60*9327*0.00**0.00****UN*1

Neither rule is a UHCG requirement. Nothing in
docs/reference/umr-uhcg-837/ constrains how a synthetic test fixture
fabricates an extra service line; "Ruling T5-f" appears only in main's own
lineage and in no guide. This is a fixture-construction policy, and the
integration policy makes 837p-seed-registration's version authoritative.

Proof that this is a policy divergence, not a corrupt artifact
-------------------------------------------------------------
Each branch's validator accepts its own branch's batch and rejects the
other's. Both validators were run against both artifacts on 2026-08-23
(main's scripts extracted read-only from git into a temp directory; the
working tree was not modified):

  merged validator      exit 0, 15/15 PASS         exit 1, FAILED [8, 9, 14]
  main's validator      exit 1, FAILED [9, 14]     exit 0, 15/15 PASS

A corrupt file would fail both. Batch 7 fails only the checks that compare it
against a generator it was not produced by, and passes every check that reads
the file on its own terms - envelope, identifiers, math, identity, encoding.

------------------------------
- scripts/generate.py splice_to() was NOT changed to make Batch 7 pass.

- Batch 7 was NOT retired, tombstoned or regenerated.
- No identifier was consumed and no new batch was created.
- validate.py was NOT weakened, and no check was skipped or downgraded.

Only the evidence text was changed, so that what is committed matches what
the committed code actually does.
